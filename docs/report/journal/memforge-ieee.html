ABSTRACT

MemForge is a deterministic simulator of an operating-system memory manager, written in C17 and also compiled to WebAssembly. It covers contiguous allocation (First-, Best- and Worst-Fit, splitting, coalescing, sliding compaction) and demand paging (single-level page tables, address translation, FIFO, LRU and OPT replacement). Policies only decide and engines only mutate, and every change is published as an event, so identical inputs and seeds always produce byte-identical traces. On 30 seeded workloads at 90% utilisation, Best-Fit reaches a 91.4 ± 0.4% success rate against 90.0 ± 0.6% for First-Fit and 87.2 ± 0.7% for Worst-Fit, while First-Fit scans the fewest holes (3.21 vs. 5.24 per request). On 2,000-reference workloads, faults follow OPT < LRU < FIFO at every frame count (103.2, 138.9 and 253.1 at 8 frames), and a frame sweep reproduces Belady's anomaly (9 → 10 faults). All eight acceptance criteria and 17 test suites pass under AddressSanitizer, UBSan and Valgrind.

The motivation is educational and experimental. Memory-management policies are usually taught with a handful of hand-worked examples, which show how a policy works but not how well it works when thousands of requests interact. MemForge lets a student replay the textbook examples step by step and then scale the same policies to large, seeded workloads, while guaranteeing that every number can be regenerated exactly on any machine.

The simulator is organised as nine small C libraries with strictly one-way dependencies. A shared kernel defines types, events and errors; two engines own the contiguous and paged state; policies are interchangeable tables of function pointers; and a single Session facade applies each operation, checks structural invariants after every step and streams events to a JSON-Lines trace writer and a metrics collector. A native command-line tool (memsim) drives experiments, and a Svelte web laboratory runs the identical engine in the browser.

Correctness is established independently of the results: textbook scenarios with hand-derived answers, invariants on every step, randomised oracles, byte-for-byte determinism checks and memory-safety tooling. The report closes with lessons learned and future work on Next-Fit, buddy allocation, Clock replacement and TLB modelling.

Keywords—memory management, deterministic simulation, contiguous allocation, fragmentation, demand paging, page replacement, Belady's anomaly.

1. INTRODUCTION

Every running program (a process) needs space in the computer's main memory (RAM) to hold its code and data. RAM is limited and shared by many processes, so the operating system must decide who gets which part of memory, give it back when a process finishes, and stop processes from touching each other's memory. This job is called memory management.

Memory management decides where each process lives in physical memory and how its addresses are translated. Textbooks present contiguous allocation and demand paging with small hand-worked examples, but the trade-offs between policies only become visible when they run on the same workload, step by step, at scale.

MemForge closes that gap. It is a modular C17 simulator with a command-line tool for scripted experiments and a browser laboratory that runs the same engine compiled to WebAssembly. Its three design pillars are summarised in Fig. 1; the rest of this paper follows the order in which the system was built: concepts, architecture, the contiguous subsystem, the paging subsystem, experiments, testing, interfaces and engineering.

3. OPERATING SYSTEM MEMORY MANAGEMENT CONCEPTS

From the ground up. Think of memory as one long row of numbered boxes (addresses 0, 1, 2, …). A program asks for, say, 212 boxes; the OS must find 212 free boxes in a row, mark them as used, and later mark them free again. Two broad strategies exist: give each request one unbroken run of boxes (contiguous allocation), or cut both programs and memory into equal-sized pieces that can be placed anywhere (paging). MemForge simulates both.

The MMU maps each logical address produced by the CPU to a physical address and traps invalid accesses. Under contiguous allocation each request receives one run of memory taken from a free hole: First-Fit takes the first hole that fits, Best-Fit the smallest and Worst-Fit the largest. External fragmentation is free memory split into holes too small to use; internal fragmentation is unused space inside a block (zero in MemForge, since granted = requested). Compaction slides blocks together to merge the holes (Fig. 4).

Why paging? With contiguous allocation, free space ends up scattered in small gaps. Paging avoids this: every piece is the same size, so any free slot fits any piece. The cost is a lookup table per program that records where each piece currently lives.

Paging splits logical memory into fixed-size pages and physical memory into equal frames; a page table maps one to the other (Fig. 5). Under demand paging a page is loaded only on its first use; a reference to a non-resident page is a page fault. When no frame is free, a replacement policy picks a victim: FIFO the oldest page, LRU the least recently used, OPT the page used furthest in the future. Belady's anomaly—more frames, more faults—can occur with FIFO but not with stack algorithms such as LRU and OPT (Fig. 6).

3.2 Why Stack Algorithms Avoid Belady's Anomaly

A replacement policy is a stack algorithm if the set of pages it keeps with n frames is always contained in the set it would keep with n+1 frames (the inclusion property). Then any reference that hits with n frames also hits with n+1, so faults can never increase. LRU and OPT satisfy inclusion; FIFO, whose contents depend on load order, does not.

6. MEMORY MODEL AND ALLOCATION STATE

In plain terms, MemForge keeps a list of memory pieces in address order; each piece is either used (owned by a process) or free (a hole). Allocation cuts a hole in two; freeing joins a piece with free neighbours so holes never sit side by side.

Memory [0, M) is an address-ordered array of ms_block records that tile it exactly. Workloads refer to blocks by stable allocation ids, never by address, because compaction moves blocks; each id passes through the lifecycle in Fig. 13, which rules out duplicate ids and double frees.

Algorithm 1: Block splitting
1:check the hole is free and size ≥ s
2:if size > s then insert a free block [start + s, end) after it
3:set size ← s, pid, alloc_id, requested; mark ALLOCATED
4:return block index
Algorithm 2: Block freeing and coalescing
1:verify the block is ALLOCATED
2:mark FREE; clear pid and alloc_id
3:if right neighbour is free then merge it
4:if left neighbour is free then merge into it

Splitting and freeing cost O(1) when no block has to shift and O(N) in the worst case (array shift); both use O(1) extra space.

7. FIRST-FIT, BEST-FIT AND WORST-FIT ALGORITHMS

When several holes are big enough, which one should be used? Picture parking a car: take the first space that fits (First-Fit), the tightest space that fits (Best-Fit), or the biggest space (Worst-Fit). Each choice affects how usable the leftover gaps will be later.

A placement policy is a pure selector: given the holes in address order and a size s, it returns whether a hole was found, which one, and how many holes it scanned (the search-cost metric). Algorithm 1 gives all three; they differ only in the selection test.

Algorithm 3: Placement selection (FF / BF / WF)
1:if view = NULL or s ≤ 0 then return (found = false, scanned = 0)
2:best ← none
3:for i ← 0 to h − 1 do
4:  if holes[i].size < s then continue
5:  FF: return (true, i, scanned = i + 1)
6:  BF: if best = none or size < holes[best].size then best ← i
7:  WF: if best = none or size > holes[best].size then best ← i
8:end for
9:return (best ≠ none, best, scanned = h)

Strict comparisons keep the lowest address on ties. All three run in O(h) time and O(1) space. Fig. 15 shows them on the textbook five-hole memory.

Excluded: Next-Fit (a roving cursor complicates coalescing and compaction for no clear gain), size-indexed trees (O(log h) but harder to keep deterministic) and the buddy system (power-of-two sizes cause internal fragmentation).

8. FRAGMENTATION AND COMPACTION

The problem. After many allocations and frees, free memory is broken into small gaps. A new request may fail even though the total free memory is enough, simply because no single gap is big enough. MemForge measures how bad this is, and can fix it by compaction: sliding all used pieces to one end so the gaps merge into one big hole, at the cost of copying data.

Algorithm 4: External fragmentation and failure cause (integer, ppm)
1:total ← Σ hole sizes; largest ← max hole size
2:if total = 0 then ext_frag ← 0 else ext_frag ← 106 − ppm(largest, total)
3:on failed request s: cause ← FRAGMENTATION if total ≥ s else CAPACITY

Example: First-Fit fails 426 with 959 free and largest hole 300, so ext_frag = 1 − 300/959 = 0.687 and the cause is FRAGMENTATION.

Algorithm 5: Sliding compaction
1:next ← 0; moves ← [ ]
2:for each allocated block b in address order do
3:  if b.start ≠ next then append (b.id, b.start, next) to moves
4:  next ← next + b.size
5:validate moves (sources match, ascending); apply; emit BlockRelocated per move
6:replace all free blocks by one hole [next, M)

Tested guarantees: the live set and total free memory are unchanged, at most one hole remains, block order is preserved, and 5,000 random layouts agree with an independent oracle.

10. PAGING MODEL AND ADDRESS TRANSLATION

Each program sees its own private virtual addresses starting at 0. Its memory is cut into pages (here 4096 bytes); RAM is cut into frames of the same size. A per-program page table says which frame holds each page. To read an address, the hardware splits it into "which page" and "how far into the page", looks up the frame, and keeps the offset unchanged.

The paging subsystem has four parts: MMU, per-process page tables, an inverted frame table and the paging engine (Fig. 19).

For a power-of-two page size S, k = log2S; vpn = va >> k, offset = va & (S−1) and pa = (f << k) | offset (Fig. 20). The full access path, including hit, fault, eviction and write-back, is Fig. 10. Faults are compulsory on a page's first use and capacity afterwards. A hit costs O(1), a fault O(F); space is O(P + F).

Algorithm 6: Paging address translation
1:validate pid and vpn; if invalid then AccessViolation, return
2:refs ← refs + 1
3:if page present then PageHit
4:else PageFault; take lowest free frame or policy victim
5:  if victim dirty then PageWrittenBack; evict; load page; update frame owner
6:set R; if write then set D
7:return pa = (frame << k) | offset

11. FIFO, LRU AND OPTIMAL REPLACEMENT

When a needed page is not in RAM and every frame is already full, some page must be thrown out to make room. A good choice throws out a page that will not be needed soon; a bad choice throws out a page that is needed again immediately, causing another fault. FIFO, LRU and OPT are three rules for making this choice.

A replacement policy keeps only its own bookkeeping and answers one question: which frame to evict. The engine calls its hooks in a fixed order (Fig. 22); ties go to the lowest frame.

Algorithm 7: Victim selection for FIFO, LRU and OPT
1:input: full frames 0..F−1, current time t
2:FIFO: return frame with smallest load_time
3:LRU: return frame with smallest last_use
4:OPT: for each frame f: nu(f) ← next index > t where its page is referenced (∞ if never)
5:       return frame with largest nu(f)
6:ties: lowest frame index; hooks update load_time on load and last_use on every access
TABLE XI

OPT evicts the page whose next use is furthest away, which can never cause an earlier fault than any other choice (Belady, 1966); it is therefore the lower bound used to judge FIFO and LRU. Because it needs the whole reference string, the session refuses OPT in live interactive runs.

12.1 Belady's Anomaly (AC-4)

With 4 frames, from the seventh reference on FIFO always evicts exactly the page needed next, so every reference faults.

Algorithm 8: Frames table for memsim refs --table
1:frames ← [empty] × F; columns ← [ ]
2:for t ← 0 to n − 1 do
3:  if ref[t] ∈ frames then mark hit; policy.on_access(t)
4:  else mark F; i ← lowest empty frame or policy.victim(t); frames[i] ← ref[t]
5:  append copy of frames to columns
6:print the reference row, one row per frame, and the fault row
Algorithm 9: Belady frame sweep
1:for F ← Fmin to Fmax do faults[F] ← run(refs, F, policy)
2:for F ← Fmin + 1 to Fmax do
3:  if faults[F] > faults[F − 1] then report anomaly point F (printed with *)

The sweep simply reruns the whole string for each frame count; the anomaly is any point where the curve rises. For the AC-4 string FIFO reports one anomaly point (F = 4), LRU and OPT none.

14. WORKLOADS AND PERFORMANCE METRICS

A workload is simply a script of memory requests (allocate, free, access a page) that is fed to the simulator. A metric is a number measured while it runs, such as how many requests succeeded or how many page faults occurred. Using the same workload for every policy makes the comparison fair.

Algorithm 10: refs-locality generator (seeded)
1:rng ← xoshiro256** seeded by SplitMix64(seed)
2:for t ← 0 to n − 1 do
3:  if t mod phase = 0 then pick a new working set of w pages
4:  if rng < pout then page ← uniform over all pages
5:  else page ← uniform over the working set
6:  emit access P0 page

The alloc-uniform generator works the same way for memory: it allocates with probability palloc (sizes uniform in [min, max]) while live memory is below the utilisation target, and otherwise frees a random live block. Integer-only arithmetic makes the output identical on every platform.

15.3 How the Confidence Intervals are Computed

Algorithm 11: Mean and 95% confidence interval over seeds
1:x1..xn ← metric for each seed (n = 10)
2:mean ← (Σ xi) / n
3:s ← sqrt( Σ (xi − mean)2 / (n − 1) )
4:half ← t0.975, n−1 · s / sqrt(n)   (t = 2.262 for n = 10)
5:report mean ± half

Because every policy runs on the same ten workload files, differences between policies are paired: seed-to-seed noise affects all policies equally, so even small gaps such as Best-Fit's 1.4-point lead over First-Fit at 90% are reliable.

Reading the two benchmarks together. E1 and E4 show the same trade-off from two sides: the policy that uses more information (Best-Fit looks at every hole; OPT looks into the future) gives the best result, while the cheapest policy (First-Fit; FIFO) is good enough at low pressure and degrades first as memory becomes scarce.

16. TESTING STRATEGY AND CORRECTNESS

Testing answers one question: does the simulator give the right answers? We check it against textbook examples whose answers are known, check internal consistency rules after every single step, run it twice to confirm identical output, and run memory-error detectors over the C code.

Randomised oracles: 5,000 compactions match a unit-by-unit oracle; no policy beats OPT; LRU and OPT never show Belady's anomaly; every fixture run twice gives equal SHA-256 trace digests (AC-6). Expected values are written into each test before it is compared with the engine, taken from the Silberschatz textbook or from Belady's original paper.

23. CONCLUSION AND FUTURE SCOPE

MemForge meets its goals: a deterministic, modular C17 simulator that reproduces the textbook examples exactly and compares policies fairly. Best-Fit gives the best success and lowest fragmentation, First-Fit is cheapest, Worst-Fit is worst on both; OPT < LRU < FIFO at every frame count, and only FIFO shows Belady's anomaly.

TABLE XXIV
Goals and evidence
AreaDeliveredEvidence
ContiguousFF/BF/WF, split, coalesce, compactionAC-1, AC-2, E1
Pagingtranslation, FIFO/LRU/OPT, sweepAC-3–5, E4
Determinismbyte-identical tracesAC-6
Correctnessinvariants, oraclesAC-7, 17/17
DeliveryCLI + wasm from one code baseweb equivalence test

Lessons: determinism must be designed in (integer state, logical clocks, tie-breaks); separating decisions from mutation made policies trivially testable; compiling the real engine to WebAssembly removed demo drift; automated layering checks caught boundary violations early.

Future work: Next-Fit, buddy allocation, alignment; Clock, LFU, a TLB and two-level tables; local replacement; Knuth's fifty-percent rule; real program traces; fuzzing and a coverage gate.

In short, MemForge turns two chapters of an operating-systems textbook into something that can be run, measured and checked: every example in the book is reproduced exactly, and every claim about which policy is better is backed by a repeatable experiment.
